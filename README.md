# qrbeam

把文件从电脑传到手机，**不经过任何网络、蓝牙或数据线** —— 电脑屏幕上高速闪动的一串二维码，
被手机摄像头逐帧"拍"下来，最后还原成完整的原文件。

数据全部走这条肉眼可见的光信道。传完之后，两边都不需要曾经连过网。

```
 电脑屏幕                                            手机摄像头
┌──────────────────┐   ┌────┬────┐   ┌────┬────┐    ┌─────────────┐
│  ██████ ▄▀ ██████│   │ QR │ QR │ → │ QR │ QR │ →  │  取景 → 分区 │
│  ██▀▀██ ▀█ ██▀▀██│   ├────┼────┤   ├────┼────┤    │  识别 → 纠删 │
│  ██████ ██ ██████│   │ QR │ QR │   │ QR │ QR │    │  → 还原文件  │
│  每帧 4 个码      │   └────┴────┘   └────┴────┘    └─────────────┘
│  10 帧/秒循环     │        第 N 帧        第 N+1 帧
└──────────────────┘
```

## 快速开始

1. 把这个目录部署到任意 HTTPS 静态托管（GitHub Pages 最省事）：
   推上去，然后在仓库设置里打开 Pages。
2. 手机浏览器打开 `receive.html`（或首页 `index.html` → 接收端），
   **允许摄像头权限**。首次打开后页面会被 Service Worker 缓存，之后没网也能用。
3. 电脑浏览器打开首页 `index.html` → 发送端，选一个文件（也可以直接拖进去）。
4. **两端选同一个「布局」**，点「开始投射」。
5. 手机上点「开始扫描」，画面上会出现一个与所选布局**同比例**的取景引导框：
   把电脑屏幕上的二维码铺满它即可，位置和距离都不需要很准。

接收端会自动锁定网格位置并实时显示每格的识别状态（绿框 = 这一格刚读到了），
进度条走完就会出现保存按钮。

> 接收端**必须**运行在 HTTPS 下 —— 这是浏览器对 `getUserMedia`（摄像头）的硬性要求，
> 跟传输本身是否需要网络是两回事。传输链路从头到尾不碰网络。

## 它凭什么快，又凭什么准

### 1. Base45 正好落在二维码的 Alphanumeric 字符表上

二维码的 Alphanumeric 模式只认 45 个字符：`0-9 A-Z 空格 $ % * + - . / :`。
Base45（RFC 9285）的字符表**与它逐字相同**，于是编码后的数据可以走
**5.5 bit/字符** 的 Alphanumeric 模式，而不必退化成 **8 bit/字符** 的 Byte 模式。

对比最常见的「Base64 + Byte 模式」方案，同样一份数据占用的模块数少约 **31%**，
换算过来就是同样一屏内容能多塞近一半的有效载荷。这是整套方案里性价比最高的一处选择。

`app/lib/base45.js` 里还保证了「字符数 ↔ 字节数」是双射，接收端仅凭二维码解出的
字符串长度就能反推出净荷长度，不需要任何额外的长度字段。

### 2. 一帧并排多个码

屏幕上按 `cols × rows` 紧铺多个二维码，手机把画面按同一套网格切成对应数量的分区，
每块单独识别。吞吐随码数近似线性增长：

| 版本 | 每块净荷 | 4 码 @ 10fps | 6 码 @ 10fps |
| ---- | -------- | ------------ | ------------ |
| v15  | 492 B    | 18.4 KB/s    | 27.6 KB/s    |
| v20  | 816 B    | 30.2 KB/s    | 45.3 KB/s    |
| v25  | 1220 B   | 45.0 KB/s    | 67.4 KB/s    |
| v30  | 1664 B   | 61.1 KB/s    | 91.7 KB/s    |

（理论值，含 1/15 的 META 插播开销，未计丢帧。）

分区向外扩展的容差有严格上限：格子里二维码内容到格子边界只留了 4 个模块的静区，
也就是格子边长的 `4/(n+8)`（版本 20 时约 3.8%）。再往外扩就会把邻码的定位图案
拉进来，jsQR 会锁错码 —— 实测正是如此。所以默认容差取 2%，并对不准的部分交给自动对齐解决。

### 3. LT 喷泉码：单向广播不重传

屏幕 → 摄像头是纯单向信道，没有任何反向链路可以让手机说"这一帧我没收到"。
而且屏摄**一定会丢帧**：相机帧率和屏幕刷新不同步、曝光瞬间的重影、手抖、反光……

所以每个分段内的 K 个源块用 **LT 喷泉码**编码：发送端持续播撒"随机若干个源块的异或"，
接收端只要累计到 K 个线性无关的方程，就能把整段还原出来。
丢帧的代价只是"再多看几帧"，永远不会卡在某个特定帧上等它重来。

实测编码开销（K = 512）：

| 整帧丢失率 | 需要发送的块数 | 实际收到的块数 | **有效开销** |
| ---------- | -------------- | -------------- | ------------ |
| 0%         | 518            | 518            | **1.2%**     |
| 20%        | 649            | 519            | **1.4%**     |
| 40%        | 859            | 515            | **0.6%**     |
| 60%        | 1299           | 520            | **1.6%**     |

注意最后一列：**不管丢多少帧，真正需要收到的块数几乎就是 K 本身**。
丢帧只是让发送端多播一会儿，不会降低编码效率。

配套的两个设计：

- **接收端可以从任意时刻中途加入**。每帧的每个码都是一条自描述记录（含会话号、段起始、
  段长度、种子），扫到哪一帧就从哪一帧开始，不需要握手、不需要同步。
- **发送端无状态**。块内容只由 `(帧号, 槽位)` 决定，所以可以随意预渲染、在 Worker 里
  并行生成、甚至重放同一帧（重放只是又给接收端一个线性相关的方程，无害）。

### 4. 两层校验

- 每条记录尾部带 **CRC-16**：屏摄里"拍到一半"的残帧非常常见，CRC 让接收端能立刻、
  廉价地丢掉它们，不让坏数据污染方程组。
- 文件头里有 **SHA-256**（周期性通过 META 记录播发）：全部收完后校验一次，
  确认结果逐字节正确。

### 5. 自动对齐与取景引导框

用户不需要把二维码对准到像素级。未对齐时画面上会显示一个**与所选布局同比例的引导框**
（发送端的画布就是 cols×rows 个正方形格子紧铺成的，外形比例正好是 cols:rows），
把电脑屏幕铺满它就行。这个框完全由取景区的实际尺寸推导，所以竖屏、横屏、地址栏收展
都会自动跟着变：竖屏拿横向布局时它会收成中间一条扁框，顺手提示你横过来更划算。

对齐的依据是 jsQR 返回的四个角点：据此算出码的边长；发送端是把码居中放在自己格子里的，
所以格子边长 = 码边长 × `(n + 2·quiet)/n`，整片网格的原点也就随之确定，多个样本取中位数抗离群。

这里有个坑值得记下来：**jsQR 在画面里同时存在多个二维码时会锁错定位图案组合**
（实测 2×2 布局下整帧扫描全部失手，而单格却完全正常）。
所以自动对齐是建立在分区扫描之上的 —— 每个分区里本来就只有一个码。

对齐成功后每帧按精确网格裁剪，既不留容差、也不会被邻码干扰；连续多帧找不到码时
（比如手机被挪动了）会自动放弃旧对齐，重新回到引导框范围内搜索。

> 另一个曾经的坑：早期版本按"手机横竖"去转置网格，那是错的。无论怎么持握手机，
> 取景预览里的画面方向都和人眼看到的一致，电脑屏幕的横向始终对应画面的横向。
> 转置之后 3×2 会被当成 2×3，每个分区都套不住一个完整的码，画出来的框也就比实际的码
> 大出一大截 —— 这正是"校准框过大"的根因。

### 6. 重活都丢给 Worker

- 发送端：`文本 → 二维码位图` 是最耗 CPU 的一步（每个码要做 8 次掩码评估，v20×4 码约 26ms）。
  放到 `sender-worker.js` 里预渲染，主线程只做 `drawImage`。
- 接收端：一帧最多要跑 8 次 jsQR，单帧耗时可达上百毫秒。整个"裁剪 + 识别"都在
  `receiver-worker.js` 里完成，主线程只做一次 `drawImage(video)` +
  `transferToImageBitmap()`（零拷贝），所以取景画面始终顺滑。

两个 Worker 都有主线程回退路径，Worker 或 OffscreenCanvas 不可用时自动降级。

## 参数怎么选

| 参数       | 建议                                                                       |
| ---------- | -------------------------------------------------------------------------- |
| 布局       | 从 `4 个码` 起步。手机近、屏幕大、画面清晰可以上 `6 个码`；老手机用 `1 个码` |
| 版本       | 换布局时发送端会自动给一个"当前屏幕装得下"的版本。v20 附近性价比最高        |
| 纠错级别   | 默认 `L`（容量最大）。屏幕有反光或有摩尔纹时提到 `M`                        |
| 刷新率     | 默认 `10 fps`。相机容易拍到换码瞬间的残影，10–12 fps 通常最稳               |
| 分段大小   | 默认 `512`。段越小进度条越早开始动，段越大整体略有优势                      |

几个实用技巧：

- 手机上每模块的等效像素数少于 3 就会开始频频失手 —— 此时应该减少码数或降低版本。
  发送端侧栏的「屏上每模块」和「理论速率」可以帮你权衡。
- 手机横着拿能让引导框撑满画面（竖屏拿横向布局时，上下会浪费一大截）。
- 显示器亮度调高、关掉自动亮度；避开屏幕上的强反光。

## 开发与测试

```bash
node --test "test/*.test.mjs"   # 64 个测试（引号让 Node 自己展开 glob，跨 shell 一致）
node tools/gencap.mjs           # 只在更换 qrcode-generator 版本后才需要重跑
```

端到端测试不是"假装"的：它真的把每一帧渲染成位图，加上高斯噪声、box 模糊、缩放，
再走一遍分区扫描和 jsQR 识别，最后逐字节比对还原结果 —— 整条光信道在没有摄像头的
情况下被完整验证，包括 55% 整帧丢失、明显失焦、以及用户对偏后靠自动对齐找回网格。

页面脚本本身也真的会被执行一遍：测试从 HTML 里抽出真实存在的 `id` 集合构造 DOM 桩，
跑 `sender.js` / `receiver.js` 的初始化，并且会实际调用接收端的叠加层绘制，
断言校准框的比例、居中、是否越界（竖屏 / 横屏 / 矮屏各一套用例）。
外加一条"反向验证"记录：把曾经那个错误的朝向转置逻辑放回去，这几个用例会立刻失败。

页面本身没有构建步骤，所有依赖都以普通 `<script>` 内联，双击 `send.html`
（`file://`）也能直接用发送端；接收端因为要用摄像头，必须走 HTTPS。

## 已知限制

- 速率受限于屏幕尺寸和手机摄像头素质，实用区间大约 20–80 KB/s。
  几百 KB 的文件十几秒，几 MB 的文件要几分钟 —— 不适合传大文件。
- 传输期间两端都要保持在原位；手机挪动后接收端需要重新对齐（会自动进行）。
- 电脑屏幕需要大致正对手机，明显倾斜会显著降低识别率。
- 发送端把整个文件读进内存，页面里限制在 64 MB 以内。
- 手机端需要 HTTPS 才能申请摄像头权限；`file://` 打开接收端会提示无法使用摄像头。
